# Lab 03: OLED SSD1306 (I2C 모드, 주소 자동 감지)

## 1. 개요

보드는 **ESP32-S3-DevKitC-1** (`esp32s3_devkitc/esp32s3/procpu`), 프레임워크는 **Zephyr RTOS**를 사용합니다.

0.96인치 SSD1306 128x64 모노크롬 OLED를 **I2C 모드**로 구동합니다. SSD1306 I2C 모듈은 실장된 저항(SA0 스트랩)에 따라 **0x3C 또는 0x3D** 두 주소 중 하나로 동작하는데, 이 랩은 Lab 01(I2C bus scanner)과 같은 방식으로 부팅 시 두 주소를 직접 스캔해서 실제로 응답하는 쪽을 자동으로 골라 씁니다.

이 랩은 Zephyr의 Display/CFB 서브시스템이나 in-tree `solomon,ssd1306` 드라이버를 쓰지 않고, **Lab 02(PCF8574 LCD)와 동일하게 raw I2C**로 SSD1306을 직접 제어합니다.

> ℹ️ **이 랩은 이전에 파킹했던 SSD1306 I2C 랩(로드맵의 "보류 중" 항목)과는 별개의 새 구현입니다.** 다른 보드(Synaptics SR110)에서 실기로 완전히 검증된 참고 구현을 기반으로 새로 작성했고, 그 구현에서 실제로 발견/수정된 두 가지 버그 수정 사항(3절, 8절 참고)을 그대로 가져왔습니다. 파킹된 랩의 하드웨어 미스터리(화이트 노이즈)를 이 코드가 자동으로 해결한다는 보장은 없지만, 이전 버전에는 없던 수정 사항이 반영되어 있으므로 재시도할 가치가 있습니다.

## 2. 왜 raw I2C인가 (Zephyr 표준 드라이버를 안 쓰는 이유)

Zephyr의 `solomon,ssd1306` 드라이버는 devicetree 노드에 `reg = <0x3C>;`처럼 **주소를 빌드 타임에 고정**해서 씁니다. 그런데 이 랩의 목적 자체가 "부팅 시 실제 연결된 주소를 스캔해서 자동으로 고르는 것"이라, 애초에 정적 devicetree 바인딩과는 맞지 않습니다. 그래서 이 랩은 devicetree에 SSD1306 노드를 아예 선언하지 않고 `main.c`에서 직접 I2C 명령/데이터를 씁니다.

## 3. SSD1306 I2C 프로토콜 요약 (+ 프레임버퍼 전송 방식에 대한 중요한 주의)

SSD1306과의 모든 I2C 트랜잭션은 **컨트롤 바이트**로 시작합니다:

| 컨트롤 바이트 | 의미 |
|---|---|
| `0x00` | 뒤따르는 바이트(들)는 **명령(command)** |
| `0x40` | 뒤따르는 바이트(들)는 **픽셀 데이터(GDDRAM)** |

명령은 한 번에 하나씩(컨트롤 바이트+명령 바이트 2바이트), 프레임버퍼(1024바이트) 전체는 컨트롤 바이트(`0x40`)를 맨 앞에 붙인 **1025바이트를 하나의 `i2c_write()` 트랜잭션**으로 보냅니다.

> ✅ **참고 구현(SR110)에서 실기로 확인된 이슈**: 참고 구현의 최초 버전은 프레임버퍼를 복사하는 비용을 아끼려고 `i2c_transfer()`로 컨트롤 바이트(메시지1)와 프레임버퍼(메시지2)를 "STOP 없이 이어붙이는" 2-메시지 방식을 썼습니다. 그 보드에서는 코드가 에러 없이 완료됐는데도 화면에 텍스트 대신 **노이즈 형태의 점들**이 나오는 문제가 재현됐습니다 — 유력한 원인은 해당 I2C 컨트롤러가 메시지 사이에 원치 않는 STOP/새 트랜잭션을 끼워 넣어서, SSD1306이 컨트롤 바이트 하나짜리 트랜잭션과 (프레임버퍼 첫 바이트를 새 컨트롤 바이트로 오인식하는) 두 번째 트랜잭션으로 쪼개 해석했기 때문으로 추정됩니다.
>
> 이 랩은 처음부터 **컨트롤 바이트+프레임버퍼를 하나의 연속된 버퍼로 합쳐서 단일 `i2c_write()`**로 보내도록 작성했습니다 — ESP32-S3의 I2C 드라이버에서 이 문제가 실제로 재현되는지는 확인되지 않았지만(즉 이 부분이 ESP32-S3에서도 필요한지는 미검증), 멀티 메시지 전송의 세부 동작에 대한 가정 자체를 없애는 더 안전한 기본값이라 그대로 채택했습니다.

## 4. 배선

| 신호 | 역할 | ESP32-S3-DevKitC-1 |
|---|---|---|
| VCC | 전원 | 3.3V |
| GND | 그라운드 | GND |
| SDA | 데이터 | GPIO8 (I2C0 SDA, 시리즈 통일 핀) |
| SCL | 클럭 | GPIO9 (I2C0 SCL, 시리즈 통일 핀) |
| RST (모듈에 이 핀이 **있는 경우에만**) | 하드웨어 리셋 | **보드 자체의 RST/EN 핀에 직결 (권장, 실기 확인됨)** — 아래 8-1절 참고. GPIO4 소프트웨어 토글 방식도 코드에 남아있지만 대안임 |

알리익스프레스 등에서 흔히 파는 저가 SSD1306 모듈은 대부분 **VCC/GND/SDA/SCL 4핀뿐**이고 RST 핀 자체가 없습니다 — 이 경우 위 RST 행은 무시하면 됩니다. Lab 01/02와 동일한 I2C0 버스(GPIO8/9)를 그대로 재사용합니다.

## 5. 전원/풀업 주의 (파킹된 이전 랩에서 얻은 교훈)

파킹된 이전 SSD1306 I2C 랩의 하드웨어 디버깅에서, 화이트 노이즈 증상의 유력한 용의선으로 **I2C 버스의 물리 계층(약한 내장 풀업)** 가설이 남아있었습니다. 같은 컨트롤러를 쓰는 SPI 버전(별도 워크스페이스)은 정상 동작이 확인됐으므로, 문제가 있다면 컨트롤러/초기화 로직보다는 I2C 배선 쪽일 가능성이 높습니다. 이 랩에서 스캔이 실패하거나 화면에 노이즈가 나오면, 코드보다 먼저 아래를 시도해 보십시오:

1. SDA/SCL에 **외부 4.7kΩ 풀업 저항**을 3.3V로 추가 (ESP32-S3 내장 풀업에만 의존하지 않기)
2. 모듈을 보드 헤더가 아닌 **외부 3.3V 전원**으로 구동
3. 브레드보드 배선을 최대한 짧게, 점퍼 접촉 불량이 없는지 재확인

## 6. Devicetree 오버레이

```dts
&pinctrl {
    i2c0_default: i2c0_default {
        group1 {
            pinmux = <I2C0_SDA_GPIO8>, <I2C0_SCL_GPIO9>;
            bias-pull-up;
            drive-open-drain;
            output-high;
        };
    };
};

&i2c0 {
    status = "okay";
    clock-frequency = <100000>;
    pinctrl-0 = <&i2c0_default>;
    pinctrl-names = "default";
};
```

Lab 01/02와 동일한 GPIO8/9 오버라이드 패턴입니다 — SSD1306용 자식 노드가 없다는 점(2절 참고)만 다릅니다.

## 7. 주소 자동 감지 동작 방식

```c
static const uint8_t oled_addr_candidates[] = { 0x3C, 0x3D };

static bool i2c_probe_addr(const struct device *bus, uint8_t addr)
{
    uint8_t dummy = 0;
    int ret = i2c_write(bus, &dummy, 1, addr);   /* Lab 01/02와 동일한 write 프로빙 */
    return (ret == 0);
}
```

- 0x3C를 먼저 시도하고, 실패하면 0x3D를 시도합니다 (SSD1306이 쓸 수 있는 주소는 이 둘뿐이므로 Lab 01처럼 0x08~0x77 전체를 훑을 필요는 없습니다).
- 프로빙 방식은 Lab 01/02에서 이미 ESP32-S3 실기로 확인된 **1바이트 write 프로빙**을 그대로 씁니다. (참고로 삼은 SR110 구현은 그 보드의 I2C 드라이버 특성 때문에 read 프로빙을 썼지만, 그건 그 플랫폼 한정 이슈라 여기서는 이 시리즈의 기존 관례를 유지했습니다.)
- 각 주소마다 최대 3회, 20ms 간격으로 재시도하고, `main()` 시작 시 100ms 안정화 지연을 둡니다 — 모듈의 전원 안정화(POR)가 끝나기 전에 프로빙하면 스캔이 실패할 수 있기 때문입니다.
- 찾은 주소를 이후 모든 명령/데이터 전송에 그대로 사용합니다.

## 8. 초기화 시퀀스

128x64 SSD1306의 표준 초기화 시퀀스입니다 (내부 charge pump 사용 — 대부분의 브레이크아웃 모듈은 패널 구동용 외부 Vcc가 없으므로 `0x8D, 0x14`로 내부 승압을 켭니다):

| 명령 | 값 | 의미 |
|---|---|---|
| `0xAE` | - | 디스플레이 끄기 |
| `0xD5` | `0x80` | 디스플레이 클럭 분주비 |
| `0xA8` | `0x3F` (63) | Multiplex ratio = 높이-1 |
| `0xD3` | `0x00` | 디스플레이 오프셋 |
| `0x40` | - | 시작 라인 = 0 |
| `0x8D` | `0x14` | Charge pump 활성화 |
| `0x20` | `0x00` | 메모리 어드레싱 모드 = horizontal |
| `0xA1` | - | Segment remap (컬럼 127 = SEG0) |
| `0xC8` | - | COM 출력 스캔 방향 리매핑 |
| `0xDA` | `0x12` | COM 핀 하드웨어 설정 (128x64용) |
| `0x81` | `0xCF` | 명암(contrast) |
| `0xD9` | `0xF1` | Pre-charge period |
| `0xDB` | `0x40` | VCOMH deselect level |
| `0xA4` | - | RAM 내용 그대로 표시 재개 |
| `0xA6` | - | 정상(반전 아님) 표시 |
| `0xAF` | - | 디스플레이 켜기 |

화면이 상하좌우 반전되어 보이면(모듈마다 유리 패널이 뒤집혀 실장된 경우가 있음) `0xA1`↔`0xA0`(segment remap), `0xC8`↔`0xC0`(COM scan direction)을 서로 바꿔서 재시도하십시오.

### 8-1. 하드웨어 리셋(RST) — 두 가지 방법, 보드 RST/EN 직결 쪽이 실기 확인됨

일부 모듈은 RST 핀을 부팅 직후 Low→High로 펄스해줘야 화면이 점 노이즈 상태에서 벗어납니다. 이걸 해결하는 방법은 두 가지가 있습니다.

**방법 A — 모듈 RST를 보드 자체의 RST/EN 핀에 직결 (권장, 사용자 실기 확인됨, 2026-09-02)**

SSD1306 모듈의 RST 핀을 GPIO가 아니라, 개발보드 자체의 리셋 핀(보드 실크스크린에 보통 `RST`나 `EN`으로 표기됨 — ESP32 계열 DevKitC류 보드는 대부분 이 핀이 있습니다)에 그대로 연결하면 됩니다. 이렇게 배선하면 보드가 리셋될 때(전원 인가, 리셋 버튼, 재플래시 등) OLED도 물리적으로 같이 리셋되므로:

- 코드에서 RST를 소프트웨어로 토글할 필요가 전혀 없음 (`OLED_USE_HW_RESET`을 0으로 둔 채 그대로 사용)
- 별도 GPIO를 하나도 소비하지 않음
- MCU와 OLED가 항상 리셋 타이밍이 맞아떨어짐 (부팅 시퀀스 전체가 리셋 상태에서 시작)

이 방법은 사용자가 실기로 직접 확인했습니다. 이 시리즈에서 RST 핀이 있는 SSD1306(또는 유사 컨트롤러) 모듈을 쓸 때는 **이 방법을 1순위로 권장**합니다.

**방법 B — GPIO 소프트웨어 토글 (대안, ESP32-S3에서는 아직 미검증)**

방법 A로 배선할 수 없는 상황(보드 RST/EN 핀이 이미 다른 용도로 쓰이고 있다거나)을 위해, `main.c`에는 GPIO를 직접 토글하는 방법도 남겨뒀습니다 — 참고로 삼은 SR110 구현에서는 검증됐지만, **ESP32-S3에서는 아직 실기 검증 안 됨**:

```c
#define OLED_USE_HW_RESET 0  /* 모듈에 RST 핀이 있고 방법 A를 못 쓸 때만 1로 변경 */
...
#define OLED_RST_GPIO_NODE DT_NODELABEL(gpio0)
#define OLED_RST_PIN       4
```

> 🛑 **핀 선택 주의**: RST용 GPIO를 고를 때는 회로도 넷 이름만 보고 판단하지 말고, ESP32-S3의 스트래핑 핀(GPIO0/3/45/46)과 USB-JTAG 핀(GPIO19/20)을 피하십시오. GPIO4는 이 시리즈 Lab 07의 RST 핀과 동일해서 골랐습니다.

## 10. 트러블슈팅

| 증상 | 원인 / 해결 |
|---|---|
| `No SSD1306 found at 0x3C or 0x3D` | 배선(SDA/SCL) 확인. **5절의 풀업/전원 가이드부터 시도** — 이전 파킹된 랩에서 화이트 노이즈의 유력 원인으로 남아있던 문제 유형입니다 |
| `I2C0 device not ready` | 오버레이가 실제로 적용 안 됨 — 오버레이 파일명이 west board target과 일치하는지 확인 |
| 주소는 잡히는데 초기화 중 `SSD1306 init failed` | 어느 명령에서 실패했는지 콘솔에 `ssd1306 cmd 0xXX failed, ret=N` 로그가 남습니다 — `ret` 값(음수 errno)과 실패한 명령 바이트를 확인하십시오. 전원 문제(5절)부터 의심해 보십시오 |
| 화면이 켜지긴 하는데 아무것도 안 보임 | `ssd1306_update()`가 실패 없이 리턴했는지 로그 확인. 컬럼/페이지 주소 범위(`0x21`/`0x22`)가 실제 패널 해상도(128x64)와 일치하는지 확인 |
| 주소 스캔/초기화 전부 성공했는데 화면에 노이즈만 나옴 | 3절 참고 — 이미 단일 버퍼 `i2c_write()`로 구현되어 있어 참고 구현에서 발견된 원인은 이미 반영되어 있습니다. 그래도 재현되면 5절의 풀업/배선 점검부터 하십시오 |
| 화면이 상하 또는 좌우 반전 | 8절 마지막 문단 참고 — `0xA1`/`0xC8` 극성을 반대로 시도 |
| 글자가 깨지거나 이상한 위치 | `fb_draw_char`의 페이지/컬럼 계산, 또는 폰트에 없는 문자를 쓰고 있는지 확인 (7절 폰트 테이블 참고) |
| 초기화는 에러 없이 끝났는데 화면이 계속 점 노이즈 상태 | 모듈에 RST 핀이 있다면 그게 원인일 수 있음 — 8-1절 참고. **우선 모듈 RST를 보드의 RST/EN 핀에 직결**해보고(방법 A, 실기 확인됨), 그게 안 되면 `OLED_USE_HW_RESET`을 1로 켜고 GPIO4에 연결하는 방법 B를 시도하십시오 |
